# Dawkey

A DAW for the Linux desktop, written in Rust. Wayland only, PipeWire/WirePlumber only, its own client-side window decorations (never libdecor), and MCP built in. The roadmap and architecture are in [docs/PLAN.md](docs/PLAN.md).

## Commands

- Build: `cargo build`
- Test everything: `cargo test --workspace` (includes end-to-end tests that drive the real binary over MCP)
- Lint: `cargo clippy --workspace --all-targets -- -D warnings`
- Format: `cargo fmt --all` (CI runs `cargo fmt --all --check`)
- Run the app: `cargo run -- [Project.dawkey]` opens the window (PipeWire audio unless the preferences say otherwise; `--audio virtual` for none). The window reads `$XDG_CONFIG_HOME/dawkey/preferences.json`; headless instances ignore it. It serves MCP on `$XDG_RUNTIME_DIR/dawkey/<pid>.sock`; `cargo run -- mcp --attach` bridges stdio to it (the `dawkey-live` server in `.mcp.json`).
- Plugins are found on `$CLAP_PATH`/`$LV2_PATH`/`$VST3_PATH` if set, otherwise the standard locations; the list is cached in `$XDG_CACHE_HOME/dawkey/plugins.json`. Each `.clap` file and `.vst3` bundle is scanned by `dawkey scan-plugin FILE` in its own process. The window runs plugins in processes of their own (`dawkey plugin-host`; preference `bridge_plugins`), one per plugin file shared by its instances (preference `share_plugin_processes`); headless instances run them in-process unless given `--bridge-plugins[=shared|separate]`. Plugin processes are sandboxed (preference `sandbox_plugins`; headless `--no-sandbox`).
- Run the headless MCP server: `cargo run -- mcp --headless [Project.dawkey]`. `.mcp.json` registers it as the `dawkey` server. It uses the virtual audio backend; add `--audio pipewire` to play through PipeWire (`--no-autoconnect` to leave it unlinked).
- MCP over HTTP (opt-in): the window serves streamable HTTP at `http://127.0.0.1:<port>/mcp` when the preferences say so (`mcp_http`, `mcp_http_port`, default 7381); `cargo run -- mcp --headless --http 127.0.0.1:0` serves it instead of stdio and prints the URL. Loopback addresses only; every request needs `Authorization: Bearer <token>`, the token being `$DAWKEY_MCP_TOKEN` (headless) or `$XDG_CONFIG_HOME/dawkey/mcp-token` (0600, made on first use).
- Live PipeWire tests (need a desktop session; never start the transport, so they're silent): `cargo test --test pipewire -- --ignored --test-threads 1`

## Layout

- `crates/dawkey-core`: project model, `Command` bus, undo history, project files, `Handle<T>`
- `crates/dawkey-media`: decoding (Symphonia), resampling (rubato), WAV writing, exporting (`export.rs`: a `BlockSource` streamed through resampling, analysis and TPDF dither to WAV or FLAC via flacenc, or encoded to Ogg Vorbis via vorbis_rs (vendored libvorbis; `quality` 0 to 10) or Opus via opus-pure (pure Rust; `bitrate_kbps`; always 48 kHz, pre-skip and end trim so the file plays exactly as long), with Vorbis comment `tags`), analysis (peak/RMS/LUFS/hash, also streaming: `Analyzer`), reading `.mid` files (midly)
- `crates/dawkey-dsp`: built-in real-time DSP: the polyphonic synth that plays MIDI tracks
- `crates/dawkey-plugins`: CLAP (clack-host), LV2 (lilv) and VST3 (the `vst3` crate's bindings; `vst3/`: the module and factory, Dawkey's host objects, the plugin's component and controller, the processor, the instance) hosting: scanning into a `Catalog`, `Host::load` → control-thread `Instance` + real-time `PluginProcessor`; the LV2 worker (`lv2_worker.rs`: a thread of its own, or the work done as it's scheduled for offline renders and the virtual clock, so they stay deterministic; also during `restore`); atom port buffers as big as `rsz:minimumSize` asks; the out-of-process bridge (`bridge/`: shared memory and futexes, the socket protocol, the `plugin-host` side, and the `BridgedProcessor` that stands in on the audio thread); what CLAP and VST3 share: ports and their buffers (`ports.rs`), note expressions (`expression.rs`), timers (`run_loop.rs`)
- `crates/dawkey-test-plugins`: tiny CLAP, LV2 and VST3 plugins (one cdylib) with exact outputs, for tests; `install()` lays them out for `CLAP_PATH`/`LV2_PATH`/`VST3_PATH`, and `vst3_id("gain")` gives a VST3 one's ID
- `crates/dawkey-engine`: compiled `Graph` (tracks and buses in dependency order, the master last; per track: sources, or what's sent to a bus → insert plugins → fader/pan → delay that lines it up where it goes; see `mix.rs` and `graph::compensate`), real-time `EngineProcessor`, `EngineController`, offline render, live MIDI parsing (MIDI 1.0 and UMP)
- `crates/dawkey-backend-pipewire`: `pw_filter` node (raw FFI: audio ports, `midi_in`, and a pool of MIDI device ports, `midi_in_N`/`midi_out_N`, made before connecting and assigned to devices by `MidiPorts`; `pw_filter` can't add ports safely while running) plus a router that links it to WirePlumber's default sink and source, and to MIDI devices
- `crates/dawkey-studio`: `Studio`, a running instance (session + decoded media + plugins + engine + backend)
- `crates/dawkey-ui`: widget tree with stable IDs, flex layout, input routing, `Scene` display list, accessibility tree
- `crates/dawkey-text`: cosmic-text with the embedded Noto fonts (`crates/dawkey-text/assets/fonts`, OFL); never system fonts
- `crates/dawkey-render`: wgpu (Vulkan) renderer for scenes: window surface or offscreen image
- `crates/dawkey-app`: `App` (studio + UI + renderer) shared by GUI and MCP; the main window's views (arrange, mixer, piano roll), dialogs (export, preferences, recovery) and click actions; `Preferences` (`prefs.rs`), the MCP token and the `McpHttpServer` the preferences drive (`mcp_http.rs`), and the dark and light palettes (`theme.rs`)
- `crates/dawkey-wayland`: the Wayland window (SCTK plumbing, our own decorations, fractional scale, cursor shapes)
- `crates/dawkey-mcp`: MCP server (rmcp 3.x), stdio and Unix-socket transports, and streamable HTTP (`http.rs`: hyper on a loopback port, a bearer token, rmcp's Host and Origin checks; `HttpServer` is what the window's preferences start and stop)
- `crates/dawkey-testkit`: `Harness`, an MCP client for end-to-end tests (over stdio, or HTTP with `headless_http`)
- `src/main.rs`: the `dawkey` binary
- `tests/`: end-to-end scenarios driven over MCP

## Rules

- **Every project mutation is a `dawkey_core::Command`.** GUI, MCP and tests all go through `Session::execute`. Never mutate `Project` directly from a frontend.
- **Adding a command:**
  1. Write an argument struct in `crates/dawkey-core/src/command.rs` that derives `Serialize, Deserialize, JsonSchema`, with `#[serde(deny_unknown_fields)]`.
  2. Write a `lower` method that validates the arguments and returns primitive `Edit`s. Add a new `Edit` variant only if no existing one fits.
  3. Add the struct to the `commands!` list.

  It then becomes an MCP tool automatically. Its doc comment is the tool description, so write it for a model reading the tool list.

- Bad tool input must return a tool error (`is_error: true`) with a readable message, not a protocol error, so a model can see the message and retry.
- One tool call is one undo step (the `batch` tool runs several commands as one: `Session::execute_batch_with` makes each command from the outcomes so far, so `"$0.track"` references resolve, and `Studio::execute_batch_with` checks plugin commands along the way). Track IDs are never reused, so they stay valid across undo and redo. `Session` logs every change (`changes.rs`: revision, kind, label, what it touched; the last thousand) for `get_changes`; every MCP result carries `revision` and `dawkey_mcp::INSTANCE_ID`, and a client subscribed to the `dawkey://project` resource gets `notifications/resources/updated` when the revision moves past the one it last saw (a poll per connection, `DawkeyMcp::on_initialized`).
- In `mcp` mode stdout carries the protocol. Log through `tracing` (to stderr, filtered by `DAWKEY_LOG`) and never `println!`.
- Every source file starts with `// SPDX-License-Identifier: AGPL-3.0-or-later`.
- **Real-time code** (`EngineProcessor::process` and everything it calls, the PipeWire `on_process` callback) must never allocate, free, lock or block. Debug builds and dawkey-engine's tests install `assert_no_alloc::AllocDisabler`, which aborts on allocation inside `process`. Graphs reach the RT thread and leave it through `rtrb` queues; the controller frees them.
- Studio changes the project only through `Studio::execute`/`undo`/`redo`/`replace`, which recompile the engine graph when the session revision changes.
- Golden audio hashes in `tests/mcp_audio.rs` pin the engine's output. If a change alters the output on purpose, update the constant and say why in the commit.
- Unsafe code is confined to `dawkey-backend-pipewire` (pw_filter FFI), `dawkey-wayland` (creating the wgpu surface from raw Wayland handles), `dawkey-plugins` (loading plugins; LV2 features, ports and atoms; VST3's COM interfaces; the bridge's shared memory, futexes and descriptor passing) and `dawkey-test-plugins` (the LV2 C ABI, VST3's COM interfaces); every other crate is `#![forbid(unsafe_code)]`.
- **Widget IDs are a public interface** (MCP `ui_*` tools and tests use them): `window/*`, `transport/*`, `view/arrange|mixer|piano_roll`, `toolbar/*`, `arrange/*` (incl. `arrange/add_track|add_midi_track|add_bus`), `timeline/ruler|lanes`, `tracks/empty`, `track/<id>` (header), `track/<id>/{name,mute,solo,gain,meter,lane,strip,fader,pan}`, `clip/<id>`, `clip/<id>/{start,end}` (trim handles), `clip/<id>/name`, `track/<id>/{monitor,takes}` (input monitoring, take lanes toggle), `track/<id>/take/<n>` (take lane header) and `track/<id>/take/<n>/lane`, `take/<id>` (a clip in a take lane), `master/*`, `status/*`, `confirm/{save,discard,cancel,backdrop}` (the "save changes?" dialog), plus `transport/record|loop|punch`, `track/<id>/arm`, `timeline/loop|punch`, `track/<id>/{automation,add_plugin,plugins}`, `track/<id>/auto/<n>` (lane header) and `track/<id>/auto/<n>/lane`, `auto/<track>/<n>/<point>`, `plugin/<id>` (mixer slot), `plugin/<id>/{bypass,remove,reload,gui}` (`reload` when it crashed or failed; `gui` toggles its own GUI, when it has one), `plugin/<id>/param/<param>` and `.../automate`, `plugin_picker/{close,rescan,list,search,scrollbar,filter/<all|effects|instruments>,item/<n>}` (`item/<n>` is the `n`th plugin shown, best search matches first), `plugin_editor/{close,params,scrollbar}`, `overlay/backdrop`, and in the piano roll `piano_roll/{grid,keys,ruler,close,quantize,grid/<4|8|16|32>}`, `note/<id>`, `note/<id>/end`, `note/<id>/velocity`, `piano_roll/{lane,lane_kind}`, `piano_roll/point/<n>`, `track/<id>/synth/<saw|square|triangle|sine|attack|decay|sustain|release|cutoff|resonance|env>`, `track/<id>/{midi_in,midi_in_channel,midi_out,midi_out_latency}`, `track/<id>/output` (mixer: master or a bus), `track/<id>/sends`, `track/<id>/send/<bus>` (an aux send: drag sets its level, Ctrl-click removes it) and `track/<id>/add_send`, the master strip's `track/0/{fader,gain,mute,plugins,add_plugin}` (with `master/strip`, `master/strip_meter`), `transport/automation` ("Auto") and `transport/automation_mode` (touch, latch, write; shown while Auto is on), `plugin/<id>/{sidechain,output/<n>}` (in `plugin_editor/routing`), `plugin_picker/status`, and the tempo lanes: `arrange/tempo`, `tempo/{lane,header,up,down,ramp,remove,value}` (`value` is the BPM field), `tempo/<n>` (point `n`, 0 is the start tempo), `meter/{lane,header,remove}`, `meter/{numerator,denominator}/{up,down|value}` (`value`: text fields), `meter/<n>`, exporting: `toolbar/export` (when there's room; Ctrl+E), `export/{format,bits,rate,range,tail,cancel,start,backdrop}`, `status/{export,export_cancel}`, the preferences: `status/preferences` (Ctrl+,), `prefs/{close,backdrop,audio,autoconnect,record_offset,autosave,autosave_every,theme,scale,mcp_http,mcp_port,mcp_token,mcp_status}`, `prefs/plugins/{bridge,share,sandbox,add_clap,add_lv2,add_vst3,rescan}`, `prefs/plugins/folder/<clap|lv2|vst3>/<n>`, `prefs/plugins/remove/<clap|lv2|vst3>/<n>`, and the recovery dialog `recover/{recover,discard,backdrop}`; double-clicking `track/<id>/midi_out_latency` or `plugin/<id>/param/<param>` turns that slider into a text field with the same ID, and double-clicking `track/<id>/name` (arrange or mixer) or `clip/<id>/name` (F2: the selected clip's) does the same for the name (Ctrl-clicking a parameter sets its default). Don't rename them casually; give new interactive widgets IDs.
- Opening another project or closing the window over unsaved changes goes through `App::request_action`/`request_close`, which show the "save changes?" dialog (`ViewState::confirm`); `App::proceed` carries the action out, also after a save dialog the dialog asked for (`PlatformRequest::ChooseSaveLocation { then }`).
- Continuous gestures (fader/pan/synth slider drags) apply live through `Studio::execute_merging` with a per-gesture key and end with `end_merge`, so a whole drag is one undo step. With "Auto" (`ViewState::automation_write`) on while playing, fader, pan and plugin parameter gestures write their automation lane at the playhead instead (`auto_write.rs`: `write_automation` over the stretch the gesture covered, merged; `App::tick` keeps writing while a control is held still), and faders and pan show their lane's value at the playhead. `ViewState::automation_mode` says for how long: touch (while held, one undo step per gesture), latch (from the grab until the transport stops) or write (every lane from where playback starts; then back to touch); a latch or write pass is one undo step (`ViewState::pass`), and each tick's writes recompile once (`Studio::execute_merging_all`). Clip, clip edge, note and tempo/meter point drags preview in `ViewState` and commit one `move_clip`/`trim_clip`/`edit_midi_notes`/`set_tempo_map`/`set_time_signature_map` on release (tempo edits re-time MIDI clips, so they never apply live). In the window clips never overlap: moves, Ctrl-drag copies (`duplicate_clip`) and Ctrl+V pastes go to the nearest space they fit in (`Track::free_start`), and trims and Ctrl-drag repeats (`repeat_clip`) stop at the next clip; MCP's clip commands place clips exactly (takes overlap on purpose).
- **Plugins**: a slot's processor lives in the engine graph and moves to the next graph by its instance key (`mix::carry_over`); its `Instance` stays in `dawkey-studio`'s `Plugins` and is unloaded when the engine hands the processor back (`EngineController::take_retired_plugins`). Plugin code on the audio thread runs inside `assert_no_alloc::permit_alloc` (plugins may allocate; the engine may not). CLAP instances aren't `Send`, so `Studio`/`App` stay on the thread that made them (headless: `Handle::spawn_thread_with`). `Studio::execute` checks plugin commands against the catalog (installed? parameter in range?). Offline renders get fresh instances (`render_job` → `finish_render`). Tests use `dawkey-test-plugins`, never the system's plugins: `install()` plus `CLAP_PATH`/`LV2_PATH`/`VST3_PATH` for the binary, or `Studio::set_plugin_search` in-process.
- **Plugin bridge**: with a `BridgeProgram` (`StudioOptions::plugin_bridge`, `Studio::set_plugin_bridge`), `Host::load_for` loads the plugin in a `dawkey plugin-host` process with an ordinary in-process `Host` there: the instances of one plugin file (`PluginInfo::path`) share a process (`BridgeProgram::share`, the default; `bridge::Processes`), or each has its own (`--bridge-plugins=separate`, preference `share_plugin_processes`). A crash takes down every instance in its process. The socket (its stdin) carries requests and replies as JSON frames with a blob, each in an `Envelope` naming the instance (`bridge/proto.rs`; a `Load` frame is followed by the instance's memfd), and each instance's memfd carries one block at a time to an audio thread of its own (`bridge/shm.rs`); the process exits with its last instance. Before loading anything, a process enters its sandbox (`bridge/sandbox.rs`, `BridgeProgram::sandbox`): Landlock lets it write (and connect to Unix sockets) only in the XDG config/cache/data/state folders, `~/.lv2`, `~/.vst3/presets`, `/tmp`, `/var/tmp`, `/dev`, `/proc/self` and Dawkey's plugin files folder (plus the X11, Wayland and system-bus sockets), no TCP, and keeps signals in (not abstract sockets: libxcb reaches the X server through one); seccomp fails ptrace and other processes' memory, kernel modules, mounts, namespaces, BPF, io_uring and AF_INET/AF_INET6/AF_PACKET sockets. Reading is allowed everywhere (samplers). `get_plugin` says `sandboxed`. The audio thread never waits: `BridgedProcessor` takes back the block the process did and hands it this one, out of a FIFO one engine block deep (the latency it reports; it grows if a block is longer, and `Plugins::idle` recompiles), so a late block is silence and a dead process passes audio through (`Instance::crashed`, `Studio::reload_plugin`). The plugin process's audio thread runs real-time one priority below Dawkey's audio thread, and only when that one is (`bridge/realtime.rs`: the kernel; else rtkit, or the portal in a Flatpak, from a helper thread that asks again while rtkit is busy). Offline renders and the virtual clock wait for each block instead (no added latency, deterministic). Tests: `crates/dawkey-plugins/tests/bridge.rs` (with the `dawkey-plugin-host` binary) and `--bridge-plugins` E2E.
- **VST3**: a `.vst3` bundle's binary (`Contents/<arch>-linux/<name>.so`) is loaded once per process and never unloaded (`vst3/module.rs`); a plugin is its component and its edit controller (one object or two, connected through their `IConnectionPoint`s), made, set up (`setBusArrangements` → `setupProcessing` → `activateBus` → `setActive` → `setProcessing`) and shut down by `vst3::plugin::Plugin`, which the instance and the processor share: whichever goes last shuts it down. Parameters in the catalog are those that can be automated (or pick a program), not hidden, read-only or bypass (that leaves out JUCE's and Dplug's thousands of MIDI CC stand-ins); their values are VST3's normalized ones (0 to 1, or 0 to the step count), so the plugin's own text is what users read. Everything the processor hands the plugin (`IParameterChanges`, `IEventList`, buses) is made at load, with a queue for every parameter, so processing never allocates. MIDI 1.0 controllers reach parameters through the plugin's `IMidiMapping` (a table of atomics, rebuilt on `kMidiCCAssignmentChanged`); MIDI out is `LegacyMIDICCOutEvent`. The controller is kept in step with the values the processor applied (`Vst3Instance::sync`, also in `take_param_changes`), and what it does comes back through Dawkey's component handler: edits of catalog parameters as `ParamChange`s, of others straight to the processor, `setDirty` and `kParamValuesChanged` (a preset loaded in its GUI) as state changes. Edits and restarts the plugin makes while loading are dropped. Its run loop (`IRunLoop`, from the host context or its editor's frame) is served by `idle` in-process and by the bridge's poll loop.
- **Plugin GUIs** show only for bridged plugins, in the plugin host process (`bridge/child.rs` runs one poll loop: the socket, the X server, the plugin's registered fds and timers). CLAP: `gui` embedded in an X11 window the process makes (`bridge/x11.rs`, x11rb; the only X11 in Dawkey, through XWayland), else floating (X11, then Wayland), with `timer-support` and `posix-fd-support`. VST3: its controller's `IPlugView` embedded the same way (`X11EmbedWindowID`), asked for when it's first shown (a controller without one says so then); its `resizeView` gets `onSize` before it returns, and the window follows. LV2: `ui:X11UI` (`lv2_ui.rs`: dlopen, `ui:parent`, resize, idle, touch, `ui:portMap`, instance and data access). Parameter values reach it as port events from a mirror the audio thread keeps, output control ports (meters) from the processor's `Link`, and atoms both ways (`atom:eventTransfer`) through message rings (`lv2_ring.rs`): what the UI sends goes into the plugin's atom input at the start of the next block, and what the plugin writes to its atom outputs goes to the UI while it's open. A GUI that doesn't say its size (DPF's) gets the size of the window it made in ours. An X11 UI is preferred; otherwise `ui:GtkUI`/`ui:Gtk3UI` go in a Gtk window of their own (`gtk.rs`: Gtk 2 or 3 loaded with dlopen, never linked; one per process; its main loop iterated from the poll loop's GUI idle), and otherwise `ui:Qt5UI`/`ui:Qt6UI` in a Qt window of their own (`qt.rs`: Qt has no C API, so `qt/shim.cpp` is built against Qt 5 and 6 by `crates/dawkey-plugins/build.rs` where their headers are (`cfg(dawkey_qt5|6)`, `DAWKEY_NO_QT=1` skips), embedded, and loaded from a memfd when a Qt UI opens; Qt isn't linked either). Gtk and Qt UI libraries are never unloaded (`ui:makeResident`). A GUI's modal dialog (a file chooser, a message) holds up its process's main thread: requests carry numbers (`Envelope::request`), a reply that's late (2 s for questions, 10 s to show a GUI, 20 s to save) makes the instance busy instead of killed (questions get Dawkey's own answers until the late reply comes), and only a load that never finishes kills the process.
- **Parameter changes a plugin makes itself** (its GUI; CLAP param output events with gestures, LV2 UI port writes and touches) come back as `ParamChange`s (`Instance::take_param_changes`, a ring from the CLAP processor, notices through the bridge, `Studio::take_plugin_param_changes`) and `App::apply_plugin_param_changes` records them as `set_plugin_param` like the editor's sliders (one undo step per gesture, automation while writing it); the project stays the source of truth and sends the value back.
- **Plugin state**: what a plugin saves of itself (CLAP `state`, LV2 `state:interface`, VST3 component and controller state, as `DKV3` and each with its length; LV2 properties are stored with URIs, not URIDs) is `Project::plugin_states`, by slot (base64 in project files), outside the undo history like the source pool (`Session::set_plugin_state`; only present slots are saved). `Studio` captures it on save, before offline renders, when a slot leaves the project (so undo brings it back as it was), and when a plugin marks itself dirty (CLAP `mark_dirty`; VST3 `setDirty`; LV2 `state:StateChanged` on an atom output, or its UI sending it a `patch:Set` or the like); the providers restore it when they load an instance (`Host::load_with_state`). get_state leaves the blobs out (`plugin_state_bytes`). An LV2 plugin's properties beyond its parameters (`PluginInfo::properties`, from `patch:writable`/`patch:readable` in its TTL at scan time) and the keys in its saved state (`dawkey_plugins::lv2_state_properties`) show in get_plugin; `set_plugin_property` (`Studio::set_plugin_property`) rewrites the saved state with the key (`lv2_state_set`, typed by an `atom:` kind) and reloads the plugin from it, so a soundfont path or the like can be set without the plugin's GUI; not an undo step, like state. LV2 plugins get `state:mapPath`/`makePath`/`freePath` (`StatePaths`): paths under the project bundle are kept relative to it, and files a plugin makes go in `<recordings cache>/plugins/<slot>/` while Dawkey runs (where a sandboxed plugin may write, wherever the project is), saved as `plugins/<slot>/...` (`StatePaths::kept`) and copied into the bundle when saving and autosaving (`Studio::keep_plugin_files`).
- **Plugin I/O**: plugins get a `ProcessContext`: the `Transport` (CLAP transport event; LV2 `time:Position` objects when it moves), a sidechain (another track's signal after its fader, from its `tap`; when it comes through more latency than the plugin's own input, `PluginNode::pre_delay` holds the track's audio back to match, see `graph::compensate`), and `AuxBuffer`s for their other outputs that go to buses (`AuxRoute`). A plugin's first other input (VST3: aux bus) is its sidechain; its other outputs pair up (LV2) or are its other ports (CLAP) or aux buses (VST3), listed as `PluginInfo::outputs`.
- **Buses and the master**: the master bus is track 0 (`dawkey_core::MASTER`, `Project::master`, not in `Project::tracks`); `Project::track` finds it and `all_tracks` includes it, so track commands work on it (not remove, rename, solo, output). Buses (`TrackKind::Bus`) have no clips and don't record. A track's `output` is a bus (or `None`: the master), and its `sends` (`Send`: bus, `gain_db`, `pre_fader`; `set_track_send`/`remove_track_send`, automatable as `AutomationTarget::Send`) copy its signal to buses at their own levels (`SendNode` in the graph: the post-fader lanes, or `TrackNode::pre` kept before the fader, at the send's gain, lined up to the bus like a plugin's aux output). Commands refuse loops through `Project::depends_on` (outputs, sends, sidechains, plugin outputs); solo follows the signal (`Project::feeds`).
- **Scanning**: the window scans plugins on a worker thread (`StudioOptions::background_scan`; slots load once it's done, and `catalog()` still waits); headless instances and tests wait for scans, so tools see every plugin. The cache (`CACHE_VERSION`) is rescanned when `PluginInfo` gains fields.
- **MIDI**: notes and controller changes are stored in frames from their clip's start; MIDI commands take beats (quarter notes), converted through the tempo map (`Project::tempo_map`, `TempoMap::clip_frames`/`clip_beats`). Over MCP every timeline position in seconds (`*_s`, except `offset_s` and `tail_s`) can be given as `*_beats` or `*_bar` instead, and a clip length as `length_beats`: `dawkey-mcp`'s `times.rs` adds them to the tool schemas and turns them into seconds before the tool runs, and adds beats to get_state's clips, notes, controls and ranges; commands themselves only know seconds. Tempo commands re-time every MIDI clip so it keeps its beats (`command::retime`). Synth voices live in the graph's `Instrument` and are carried over to the next graph on the RT thread (`mix::carry_over`), so recompiling during playback never cuts notes. Voice tags are note IDs, or `LIVE | channel << 8 | pitch` for live input. Live `MidiEvent`s carry their device's `device_tag`; tracks with a MIDI output send through `EngineProcessor::midi_output` instead of sounding. MIDI a plugin sends goes to the next plugin that takes notes (plugins that don't, and bypassed ones, pass it on); on a track with a device, what the leading MIDI effects send goes to the device (`TrackNode::to_device_after`). MIDI to devices waits out the graph's latency less the device's own (`MidiOutput::latency_ms`, which counts toward the graph latency like a plugin's; `External::pending`, on the engine's frame clock). MIDI 2.0 per-note controllers (`Controller::Note*`, 16-bit in clips) travel as three-byte messages with a status below 0x80 (UMP opcode | channel, `dawkey_core::PER_NOTE_*`; per-note management as 0x70 with its flags) plus a 32-bit `value` on `MidiEvent`/`MidiOut`/`ControlEvent`; devices get them as UMP packets, CLAP and VST3 plugins as note expressions (and note expressions plugins send come back as per-note controllers; VST3 notes and expressions carry the note ID `channel << 7 | key`), LV2 not at all. A MIDI output device's latency is the track's `latency_ms` plus what PipeWire reports for its port (`Graph::compile_with_devices`; tests fake it with `Studio::set_virtual_midi_latency`). Recorded MIDI is placed earlier by playback latency plus what PipeWire reports for the input device's port (by each event's `device_tag`; a cycle if nothing is reported), plugin latency and the record offset (`Studio::midi_record_latency_frames`; tests fake it with `Studio::set_virtual_midi_input_latency`). Tests feed MIDI with `advance_clock`'s `midi_input` (or `Studio::queue_virtual_midi`), read sent MIDI from its `midi_output` (`Studio::sent_midi`), and fake devices with `Studio::set_virtual_midi_devices`, never a real device; live PipeWire tests mute MIDI tracks before arming them and never play to a MIDI output.
- **Recording** never touches a real microphone in tests: use the virtual backend and feed a WAV with `advance_clock`'s `input_path` (or `Studio::set_virtual_input`). Dawkey links the default audio source to its inputs only while an audio track is armed, and MIDI devices to `midi_in` only while a MIDI track is armed. An armed audio track meters its input, and plays it only with `monitor` on (`set_track_monitor`). Recordings of unsaved projects go to `$XDG_CACHE_HOME/dawkey/recordings/<pid>` and are deleted once the project is saved (copied in), replaced or closed (`dawkey_studio::cache`; folders of crashed instances are swept at startup after a week); `dawkey-testkit` gives each test process its own `XDG_CACHE_HOME`, and in-process tests use `Studio::set_recording_dir`, so tests never write to the real cache.
- **Takes**: recordings are placed as takes (`AddClip`/`AddMidiClip` with `take`): `Clip::lane` one above the clips they overlap, which are muted where the take plays (split at its edges). `comp_take` picks what plays over a range. Lanes only matter to the view; muted clips are what's silent.
- The recording path is real-time safe like playback: the audio thread pushes input frames into `rtrb` rings tagged with their timeline position (`dawkey_engine::record`); `dawkey-studio`'s recorder thread writes them to WAV, one file per contiguous segment (loop pass or punch).
- Things only the platform can do (file dialogs, decoding imports off-thread) are queued on `App` (`take_platform_requests`, `take_imports`) and carried out by `dawkey-wayland` (`dialogs.rs`); headless MCP reports requested dialogs instead and imports synchronously.
- Views are rebuilt every frame from `Studio` state; UI clicks must go through `Studio`/commands like everything else (`App::activate`).
- Text fields (`ViewState::text_edit`, `text_input.rs`): while one is being typed in it takes every key; a click or drag elsewhere sets it first. Give new ones a `TextField` variant and a widget ID. The plugin picker's search (`picker.rs`) is the exception: it filters as it's typed in, so it's no `TextField`, and while the picker is open it takes every key without Ctrl (Up/Down/Home/End move the highlight, Return adds it, Escape clears the search, then closes).
- **Colors** come from the palette in use: views read `pal().text`, `pal().accent`, ... (`theme.rs`), set by `App::rebuild` from `Theme` (dark or light; the preferences pick one or follow the desktop's `color-scheme`, which `dawkey-wayland` watches through the settings portal). Don't add color constants to views; add a `Palette` field with a dark and a light value. The dark palette is what the goldens pin.
- **UI scale** (preferences) lives in `App`: it lays out in units `zoom` times the platform's logical pixels (`WindowInfo::zoom`), dividing pointer positions (and dropped files', `handle_drop`) on the way in; `App::window()` is what the platform reported.
- **Autosave and recovery**: `App::tick` autosaves unsaved changes every couple of minutes (`Studio::autosave`) to `<bundle>/backups/autosave.json` or, for a never-saved project, its recordings folder in the cache. Saving, replacing the project and a clean exit (`Studio`'s `Drop`) delete it, so only a crash leaves one. The window offers it back (`App::offer_recovery`: `bundle_recovery` for the opened project, `orphan_recovery` for a never-saved one, whose cache folder the recovering Dawkey adopts with an `owner` file).
- **Exports** stream: `Studio::export_job` (up to 6 hours) renders a block at a time (`dawkey_engine::OfflineRender`, the same blocks as `render_offline`, so it's sample-identical) into `dawkey_media::export`, which writes beside the target and renames at the end. In the window it runs on a worker thread that `App::tick` polls.
- Window decorations are ours: never add libdecor or SCTK's decoration frames. Window-chrome behavior goes through `dawkey_ui::Chrome`/`ChromeAction` and is carried out by `dawkey-wayland`.
- Golden synth output: `GOLDEN_CHORD_HASH` in `tests/mcp_midi.rs` pins the synth like the audio hashes pin the engine.
- **Versions and releases**: each crate has a `version` of its own (not `version.workspace`), and release-plz bumps and publishes them (`release-plz.toml`, `.github/workflows/release-plz.yml`; see `packaging/README.md`), so don't bump versions by hand. A new crate that's published goes in `[workspace.dependencies]` with a `version` and in dawkey's `changelog_include`; one that isn't gets `publish = false`.
- **Commit messages are Conventional Commits**, because release-plz builds `CHANGELOG.md` and the version bumps from them: `<type>[(scope)][!]: <summary>`. `feat` (something new users can do; "Added"), `fix` (a bug fix; "Fixed"), and `perf`/`refactor`/`docs`/`test`/`ci`/`build`/`chore` for the rest ("Other"). The summary is the changelog entry: imperative, written for users, lowercase after the colon (`feat: add aux sends`, `fix(mcp): stop import_midi panicking with several replacing targets`). The scope is optional and names an area (`mcp`, `plugins`, `engine`, `ui`, ...). A breaking change (project files older versions can't read, an MCP tool renamed or removed, a widget ID changed) gets `!` and a `BREAKING CHANGE:` footer. Explain why in the body when it isn't obvious. Every commit in a PR becomes a changelog entry, so squash fixups before it's merged, and never edit release-plz's `chore: release` commits.
- `tests/golden/*.png` are screenshot goldens rendered on lavapipe. After an intended visual change: `DAWKEY_UPDATE_GOLDENS=1 cargo test --test mcp_ui`, look at the new image, and commit it.
